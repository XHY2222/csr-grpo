1. 已解决（实现缺陷）

1.1 已修复 共享适配器不是同一个对象

最初 actor_bank 与 judge_bank 各自持有一个名为 shared 的 LoRA，两者只是取值相同的独立张量。这样 r_S>0 时裁判梯度并不会污染 Actor，2×2 中的 E_10 − E_00 会恒为 0——整个"跨角色参数污染"假设会被人为抹掉。

修法：把共享适配器提成 ToyModel.shared 的单一 module 实例， 两个视图共用；测试 test_shared_architecture_really_shares 断言 actor['shared.B'] is judge['shared.B']。

1.2 已修复 阶段内冻结裁判导致 warm-up 无参数可训

Dual-Adapter 要求"阶段内冻结裁判"，最初的实现方式是建优化器时直接排除裁判参数， 于是 warm-up 拿不到任何裁判参数，loss 从 1.529 走到 1.570（完全没学）。

修法：冻结由优化器的使用表达而不是 requires_grad：warm-up 优化器始终存在， 阶段内不 step 它。这也保留了 E2 诊断所需的裁判梯度。

1.3 已修复 warm-up 学习率与 GRPO 学习率混用

裁判 warm-up 是规则扰动负例上的 BCE，与策略梯度不是同一个优化问题。沿用 train.lr = 1e-5 时 60 轮几乎不动（1.529 → 1.570）；改为独立 train.warmup_lr = 3e-3 后降到 0.72（1e-2 可到 0.16）。已在 TrainingConfig 中单列。

1.4 已修复 玩具 Actor 的 base 本身是 oracle

最初 actor_logits = h @ W_s，而 W_s 正是该阶段 gold 的定义。于是 每个阶段起点准确率都是 1.000，适配器学不到任何东西，所有方法给出完全相同的结果 （实测 dual_adapter／rler_faithful／judge_lora_ensemble 都是 forward 0.530、logic 1.000、code 0.060）。这不是"方法等价"，而是夹具没有区分度。

尝试与纠正：先试了对 h @ W_s 乘 base_scale——无效， 因为正标量缩放不改变 argmax（实测 bs = 0.15/0.35/0.60 都是 1.000）。 最终改为与冻结随机头混合：base = (1−s)·oracle + s·h@W_rand， s = 0.5 时起点约 37.5%。

仍未彻底解决：即便起点不再是 oracle，40–200 步训练后各方法依然靠得很近， 且裁判与 gold 的相关性只有 ρ ≈ −0.16。见第 3 节开放问题 Q1、Q2。

1.5 已修复 ΔL_old 的梯度恒为零 / 键名不匹配

三个独立缺陷叠在一起，表现为 ΔL_old^(1st) 与投影比恒为 NaN：

  1. 目标选错：最初以 gold token 做 one-hot 交叉熵，梯度结构性接近 0。 改为在 实际采样答案 上按 gold 正负加权。
  2. 键名不匹配：TrainingState.param_delta 用 named_parameters()（actor_bank.actor.B），而梯度用 view_parameters()（actor.B）——交集为空，内积永远是 NaN。
  3. 子空间退化：只有一条梯度时 U_old 秩为 1，投影比必然接近 1 而失去意义。 改为按 prompt 堆叠成 (N, D) 矩阵再取 SVD。

现在四个臂都能给出有限的 CosSim、ΔL_old^(1st) 与投影比。

1.6 已修复 被拒绝的 L3 请求被计入"训练期 gold 调用"

gold_calls_in_training 原本统计所有处于训练作用域内的 L3 记录，包括被拒绝的。 明文违规会显示为"1 次 gold 调用"，与"成功泄漏 1 次"无法区分。现在只计 granted=True 且不属于 gold-control 的记录。

1.7 已修复 E1 浅拷贝配置串味

run_arm 用 Config(**cfg.__dict__) 复制配置，嵌套 dataclass 仍是同一对象。 E1 连续跑四个臂，前一个臂的 reward_source 会污染后一个。已改 copy.deepcopy。

1.8 已修复 RolloutBatch.collapse 把时间轴吃掉

P=1 时 (1,G,T).reshape(P*G, *shape[2:]) 得到一维张量， 随后 sequences[:, :prompt_len] 报 "too many indices"。 现在 collapse() 幂等，且 trainer 内部强制一次折叠，保证协议 A 的四个分支 看到的永远是同一个 batch（测试用 fingerprint 断言）。

1.9 已修复 CLI 路径未限制线程数导致近乎挂死

同一段 E2 代码，直接调用 run_protocol_a 用时 1.4 s；经 python -m csr_grpo.cli e2 调用则 115 s 内跑不完，faulthandler 显示卡在 judge_score_matrix 的小矩阵乘法上。 原因是剧本脚本里手动设了 torch.set_num_threads(4)，而 CLI 没有——本机 192 核， 每个 (64,16) 的矩阵乘都在争抢 OpenMP 线程。

修法：_prepare() 统一按 runtime.num_threads 设置线程数。 修复后 CLI 的 E1、E2 均在数秒内完成。

1.10 已修复 监督更新与策略梯度共用学习率

SFT/SDFT 是演示上的交叉熵，与 GRPO 不是同一个优化问题。沿用 train.lr = 1e-5 时 30 步后演示准确率仍是 0.141 → 0.141（完全冻结）；1e-2 下 100 步到 1.000， 60 步到 0.922。已单列 train.sft_lr，与之前的 warmup_lr 是同一类错误—— 同一个 lr 被三种不同的优化问题共用。

1.11 已修复 Row 2b 的 ICL 教师恒等于学生

玩具 Actor 原本是严格逐行的：actor_logits 只看当前这一行的 prompt token。 于是把 demo 拼到前面不产生任何影响，sdft_icl 的教师分布与学生的 KL 实测精确为 0，训练是空转，结果与未训练模型完全一致。

修法：给 actor_logits 加可选 context_ids， 经固定随机投影 tanh(ctx·P) 平移隐状态（缩放 0.5）。 实测上下文使 logits 偏移 0.507 并改变 argmax，KL 从 0 变为 0.141。 context_ids=None 时路径逐位不变，已有结果不受影响。

1.13 已修复 Bootstrap 置信区间被单个 NaN 重采样摧毁

E1′ 的 Gold 臂 200 次重采样中有 1 次抽到的题目全是退化组，此时 Acc_rank 分母未定义、nanmean 返回 NaN； np.quantile 遇到 NaN 会把整个置信区间变成 NaN。结果是 delta_switch_gold 点估计 −0.2092 而 CI 为 [nan, nan]—— 一个有效结果被静默丢弃，而且不报错。退化组比例一高就会触发。

修法：percentile_ci 丢弃未定义的重采样并在 BootstrapCI.n_dropped 中计数，而不是静默传播 NaN。 修复后 E1′ 给出 [-0.369, -0.069]（200 次中丢弃 14 次），退化密度变得可见。

1.12 已修复 Row 4 / Row 9 曾与普通基线完全等价

icl_judge 的 k_shots 和 static_mix 的 stages 从未被训练代码读取，两者实际上就是 dual_adapter 的副本——主表会因此错三行。

修法：plan 增加 icl_judge / static_mix 标志； Row 4 在评分时把 demo 作为上下文传给冻结裁判，Row 9 每步从所有阶段抽取 prompt 并传 逐行 stage_ids。三条路径现在结构上不同（见 §5）。

1.14 已修复 Row 6 熵过滤把该丢的轨迹留下了

entropy_filter_mask 里 score = −mean(logp) 表示熵（越大越不确定）， 但排序用了 descending=True 再取前 k。于是"保留低熵轨迹"实际保住了 最不确定的那批，正好与 M-GRPO 的意图相反；而且这个函数没有任何测试，端到端跑通不会暴露它。

修法：改升序，并加测试用三档确定性的合成 batch 断言只保留置信样本。 同时 apply_entropy_filter 里的 keep.cpu().numpy() 触发本机 Numpy is not available（见 §0），已改走 compat.to_np， 并新增掩码长度与优势行数的显式校验。

1.15 已修复 HF 后端与 Runner 的接口断档

backends/hf.py 原本只有 lora_configs / completion_mask / genrm_reward / sample / logprob / judge_scores，而 Runner 实际调用的是 六个不同的方法：set_stage、actor_logits、 judge_score_matrix、gold_score_matrix、judge_bank、 以及 warm-up 里的裁判打分。也就是说 build_backend("hf") 能返回对象， 但把它交给 Runner 会在第一次训练步就 AttributeError—— 这正是"集群冒烟跑一次就知道了"的那类问题。

修法：补齐协议层，并把后端差异压在 backend 内部：

  • set_stage：真实 LM 没有阶段条件，阶段由 prompt 和"训练哪些适配器"表达； 保留该属性只为让 Runner 不需要分支。
  • actor_logits：返回末位 next-token logits (N, V)； 显式拒绝 context_ids，因为 HF 的条件化是文本层的——静默忽略会让 Row 4 / 2b 看起来"已实现"而其实什么都没条件。
  • judge_logits / judge_score_matrix：真实裁判回答 yes/no， 输出宽度是 2 而不是词表大小；形状对齐 toy 的 (P, G)。
  • gold_score_matrix：没有注入验证器时直接报错。 返回零矩阵会被读成"所有答案都错"，污染下游所有指标。
  • judge_bank：_ParamView 用同一批张量对象注册， 因此 ModuleState.capture/restore 能写回活模型（已测）。

同时把 toy 侧补了 judge_prob（"答案更好"的 (0,1) 概率）， warm-up 的 BCE 改走它——否则两个后端会用两个不同的目标函数训练裁判， 而账本上看不出任何异常。

这些方法不需要权重即可测试：测试注入假 tokenizer 与假 PEFT 形状模型， 断言输出宽度、方向、拒绝路径与快照往返。本机已跑通 10 项。

1.16 已修复 后端协议缺失：缺方法直到第一步训练才报错

Runner.__init__ 直接构造 ToyModel，HFBackend 只能靠 "碰巧实现了同名方法"来工作。上一轮补完方法后仍然没有任何机制保证两者同构—— 一个后端少实现一个方法，会在 warm-up 之后、模型加载之后、第一次 train_step 里才抛 AttributeError，在集群上是几分钟才失败的浪费。

修法：新增 backends/protocol.py，把训练循环真正调用的成员列成契约， Runner 在构造时先校验世界与模型，一次性列出全部缺失项并指明后果。 Runner 也接受注入的 model=，真实后端可原样驱动同一套训练/测量代码。

协议起草时立刻抓到一个我自己写的过约束：我把 set_view 写进了必需方法， 但 Runner 从不调用它——那是 PEFT 切换激活适配器的内部机制，不是训练循环的语义。 可移植的操作是 view_parameters(view)（返回某个角色的参数），而不是修改全局状态。 把后端内部实现细节写进协议，会强迫每个后端都采用 PEFT 的世界观。

仍未完成：cfg.model.backend 还没有真正接到 Runner 上—— HF 后端需要一个 World 的题库适配器（make_prompts / correct_token / gold 都要落到真实题目的文本与验证器上）。 这取决于题库格式，属待定项，见第 3 节 Q7。

1.17 已修复 L1 路径调用了验证器（监督账本看不见的泄漏）

这是账本设计的反例，也是本轮最重要的一条。上一轮把 World 定成协议后， 我顺着它的调用点检查，发现两处在 L1 授权下调用了 world.correct_token： 

runner.warmup_judge()        →  with ledger.access(Level.L1, METHOD_WARMUP): 
                                    good = world.correct_token(stage, ids)
baselines.demonstration_batch() →  targets = world.correct_token(stage, ids)

在 toy 世界里 correct_token 就是 gold 的定义 （gold() 内部直接调用它，实测 gold(correct_token(...)) ≡ 1）。 真实后端里它是 L3 验证器的适配器。泄漏不会显示在账本上：记录写的是 L1，gold_calls_in_training 依然是 0， assert_clean() 照样通过——因为这次调用从未经过账本。 这正是"训练期 0 次 gold 调用"这一声明最容易被悄悄破坏的方式。

修法：把"演示答案"和"验证器答案"拆成两个独立接口：

  • demo_answer(stage, ids) —— L1，来自演示数据；禁止调用验证器。
  • correct_token(stage, ids) —— L3 视图，只允许 gold() / gold_score_matrix() 在训练作用域之外调用。

两处调用点改走 demo_answer，demo_answer 被写进协议必需项。 测试用一个 correct_token/gold 直接抛异常的世界，断言 warm-up、demonstration_batch、监督步三条 L1 路径仍能正常跑完—— 也就是说，这些路径在结构上够不到验证器，而不是"我们相信它们没调用"。

在 toy 上这不改变任何数字（两条路径都从同一张 W_s 取值，测试断言相等）。 它修的是接口形状：接口不改，真实后端一旦照抄这两处调用，泄漏就会被原样继承， 而所有审计仍然全绿。

1.18 已补齐 E3 只有门控判定有测试，产生这些数字的路径没有

E3Gate.evaluate 一直有测试，但它吃的是手工构造的 ArmOutcome。 真正产出这些数字的 run_arm_stages / run_e3 端到端路径没有任何覆盖—— 也就是说，"门控逻辑正确"与"门控读到的数字来自一次干净的运行"是两件事，只测了前者。

现已补齐 7 项端到端断言：

  • 两阶段跑完后账本 gold_calls_in_training == 0 且 violations 为空；
  • forgetting 确实是每个已学阶段降幅的均值，而不是末阶段准确率 （只取末阶段的实现会通过所有形状检查，却报告另一个量）；
  • forward_acc 等于各阶段准确率的均值；
  • 门控阈值读的是预注册的 2.0 / 1.5 pt，且解释文本必须点明 H3 的后果；
  • 固定 seed 下结果可复现（方法对比必须配对，隐藏的 RNG 会静默破坏这一点）；
  • seq_sft 走监督路径而非策略梯度路径——dispatch 一旦坏了， 该基线会悄悄变成一次 GRPO 运行，主表三行同时出错且不报错。

顺带修掉一个测试自身的错误：ledger.violations 返回的是记录列表而不是计数， 断言写成 == 0 会恒为假。改成 len(...) == 0 并把列表本身放进断言消息， 失败时能直接看到是哪条记录。

1.19 已修复 协议检查只看方法名，不看它能否被训练循环那样调用

上一轮加的 check_model 只问"这个方法存在吗"。实测两个后端的 sample 签名完全不同： 

toy: sample(prompt_ids: Tensor, group_size, temperature=1.0, generator=None, ...)
hf : sample(prompts: Sequence[str], group_size, temperature=1.0, max_new_tokens=256)

而 runner.py:242 的调用是 model.sample(pid, G, generator=self.rng)—— 传 token 张量、带 generator。真实后端会当场 TypeError: unexpected keyword argument 'generator'， 但协议检查全绿，因为方法确实存在。

修法：协议增加 REQUIRED_CALLS，用 inspect.signature(...).bind(...) 按训练循环的真实调用形状逐个试绑，签名不兼容同样在构造期失败并说明原因。 同时把 HFBackend.sample 改成接受 token ids 与 generator：

  • 取 generator.initial_seed() 派生每次调用的种子，前后保存/恢复全局 RNG 状态—— 否则采样会推进全局流，破坏配对臂与测量代码的可复现性；
  • 返回的掩码改成损失掩码（仅补全 token 为 1），与 grpo_loss 的期望一致；
  • context_ids 显式拒绝（HF 的条件化在文本层）。

写这条检查时它先误报了 ToyModel：getattr(instance, name) 拿到的是已绑定的方法，签名里没有 self，我又多绑了一个 None， 于是每个正确的方法都被判为"参数过多"。已修正，并留了回归测试防止再次写错。

1.20 已修复 丢弃未定义重采样不是中性的，而决策层不知道这件事

§1.13 修好了"单个 NaN 重采样摧毁整个置信区间"，做法是丢弃并计数。但这只解决了一半： 被丢掉的恰恰是"这一批题目全是退化组"的重采样，剩下的是一个条件分布—— 条件于"至少抽到一个有信息量的题目"。它的分位数偏低偏窄，而 classify_effect 照常据此给出 go 或 equivalence。

实测（acc_rank，500 次重采样，退化组占比 d）：

P_auditd=0.50d=0.70d=0.85理论 P(all degenerate)=d^P
614531631.6e-2 / 1.2e-1 / 3.8e-1
1603141.5e-5 / 3.3e-3 / 7.4e-2
240076.0e-8 / 1.9e-4 / 2.0e-2
200–400000< 1e-6

也就是说：在预注册的 P_audit 规模上这条路径永远不会触发，但 toy 与任何小样本 调试运行会触发，而且触发时不报错。这正是最难发现的一类——数字看起来正常，判定也照常给出。

修法：BootstrapCI 增加 drop_fraction 与 usable， classify_effect 在 usable 为假时直接返回 inconclusive。 理由不是保守，而是逻辑一致：go 与 equivalence 都是关于 抽样分布的断言，而抽样分布有一大块缺失时，这两种断言都不成立；inconclusive 正是预注册给"功效不足"安排的判定。

阈值取 5%。这不是一个标定过的常数，而是"明显被截断"的下限；若作者希望更严格的披露， 可改为只在 drop_fraction == 0 时允许判定——但那会让小样本调试运行全部变成 inconclusive，失去诊断价值。

1.21 已修复 E1 四臂测的不是同一批 P_audit 题，配对 bootstrap 实际未配对

这是目前影响最大的一个缺陷：它不报错、不改变任何形状、不让任何测试变红， 只会让 DID 变成一个看似合理的数。

Runner.make_context 用 seed + 500 生成 P_audit 题集，而 run_arm 传的 seed = 1000 + target_stage。于是： 

Switch 臂   (target_stage=2) → P_audit 题集 seed = 1502  → s1-1502-*
Continue 臂 (target_stage=1) → P_audit 题集 seed = 1501  → s1-1501-*

两个臂测的是完全不同的题。而 paired_cluster_bootstrap 对两臂重采样 同一个索引 i，在 A 臂对应第 i 道题、在 B 臂对应另一道题—— 所谓"配对"就此失效。bootstrap 的方差估计依赖同题配对，此时算出的 CI 既不是配对的， 也不是配对的保守近似，而是另一个量的区间。

修法：make_context 增加 audit_seed 参数， run_e1 对全部四个臂统一传 5000 + audit_stage。 测试同时固定两侧：显式 seed 时两臂题集必须逐位相同；缺省 seed 时必须有差异 （后者记录的正是缺陷本身，防止有人"简化"掉这个参数）。

toy 上这个缺陷不改变代码能否跑通，只改变数字的含义。E1′（Stage 2→3）走同一条路径， 同样修复。这也说明"端到端能跑 + 全部测试通过"完全不足以证明统计链路正确。

1.22 已修复 E2 协议 A 的三个串接缺陷：退化臂是空操作、Adam 动量污染、梯度裁剪含裁判

检查 ΔL_old^(1st) 的预测力时，三个独立缺陷一起暴露——它们各自不报错，合起来让协议 A 的全部读数失效。

(a) 退化臂 (iv) 是 (i) 的精确副本。

degenerate_zero 是 AdvantageConfig 的字段，但 run_protocol_a 只改了 plan.reward_source，没改 degenerate_zero——它是 plan 的属性，对 dual_adapter 恒为 False。于是四臂里有一臂根本没做它声称的事， dL、cos、adv_std 与 self 逐位相同。 修法：_arm_advantage_config 按奖励源派生 degenerate_zero。

(b) "锁死 Adam 状态"没有零掉动量，gold 臂的整个 Δθ 是继承来的动量。

协议 A 要求"冻结 Adam 状态"，实现是 TrainingState.snapshot/restore。但快照里的动量是 前序训练留下的。实测：零优势的一步 grad_norm = 0 但 ‖Δθ‖ = 8.1e-5—— Adam 动量在没有信号的情况下仍在推参数。gold 臂实测 adv_std = 0.0000 而 ‖Δθ‖ = 1.1e-4，所以 CosSim(Δθ, Δθ^gold) 衡量的根本不是"奖励方向的相似度"， 而是"继承了多少动量"。修法：每臂 step 前显式 zero_() Adam 的 exp_avg / exp_avg_sq / step，让 Δθ 只由本步梯度决定。

(c) 梯度裁剪把裁判的陈旧梯度也算进范数，缩放了 Actor 步长。

clip_grad_norm_(list(module.parameters()), ...) 遍历整个模型，包括裁判适配器。 warmup_judge 之后裁判的 .grad 仍在，actor_optimizer.zero_grad() 管不到它。实测：gold 臂 grad_norm = 0.362（裁判梯度），而 Actor 的真实梯度是 0。 这个假范数被拿去裁剪 Actor 的真实梯度——步长被一个与奖励无关的系数缩放。 修法：_optimized_params 只返回该优化器实际拥有的参数，裁剪只作用于它。

三处修完后出现一个新现象：gold 臂的 adv_std 仍为 0、‖Δθ‖ 现在也为 0—— 那批题全是退化组（gold 奖励恒定），梯度天然为零。这不是缺陷，是协议 A 碰到退化题目集时 本就该发生的退化情形。以前它被 (b) 的动量掩盖了。现在协议显式报告 status = "gold_arm_inactive" 与 gold_delta_norm，而不是把 NaN 埋进 cos_vs_gold 字段。

这三处都是"端到端能跑、所有数字有限、所有测试通过"的情形。协议 A 此前汇报的 CosSim ≈ 0.88 与 ΔL_old^(1st) 不能用作论文证据——它们衡量的不是 奖励机制，而是 Adam 动量的历史与裁判梯度的泄漏。修复后的读数会不同，且在 toy 退化集上 应当退化为 gold_arm_inactive。

1.23 已修复 协议 B 的"分支确实发散"测试名实不符

test_protocol_b_branches_actually_diverge 只断言对比字典里有键名 （"d_acc_old_vs_gold" in c），没断言值非零。实测验证： 六步 k_steps=6 下所有臂的对比均为 0.000，测试依然通过。 测试名叫"actually diverge"，实际是"结构存在"的检查，是一个悄悄说谎的测试。

修法：增加断言"至少一个臂产生非零对比"，并在消息里说明零意味着什么 （分支没有独立地重采样，或优化器步长没有真正改变 Actor 参数）。

toy 上 ΔAcc 经常全零是正常的：贪心 argmax 只在适配器把某条 logit 推过另一条时才改变。 因此测试检查的是至少一个臂非零，而非全部，避免因夹具规模小而产生假阴性。

修法：Runner 按 cfg.model.backend 分发：

  • "toy"（或 None）：照旧构造 ToyModel；
  • 其他：抛 ValueError("requires an explicit model= argument")—— Runner 无法自己构造一个真实后端（需要模型路径、tokenizer 路径、设备分配、gold 验证器， 这些都是调用方的决策）。后端由调用方 load 后注入 model=，文档字段记录意图。

1.25 已修复 三个核心模块没有任何测试覆盖，一测就抓到两个真实缺陷

按模块引用扫描发现，diagnostics/dual_line.py、 config/loader.py、rewards/sources.py 没有被任何测试引用—— 而它们恰好分别承载交付项 2（双测量线）、交付项 1（配置系统）、交付项 3（E2 奖励臂）。 补测时立刻抓到两个缺陷。

(a) DualLine.divergence 的文档说"在最新公共 step 上比较"，实现却是各取 latest。

两线本该在同一调度上采样，但部分运行或中断的运行会让它们停在不同 step。 此时相减得到的是两个时刻之差，却被当作"两条线的差异"报告，且不报错。 实测：A 停在 step 12、B 停在 step 14 时，函数照常返回一个有限值。 修法：取两条线 step 集合的交集的最大值，无交集时返回 nan。

(b) --set train.lr=3e-5 被解析成字符串，一路静默到优化器才引爆。

PyYAML 实现的是 YAML 1.1，指数形式要求尾数带小数点：3e-5 被读作字符串 '3e-5'（3.0e-5 才是浮点）。而 Config.validate 只做范围检查， 字符串在 0 < value < 20 处短路通过；最后在 torch.optim.Adam(lr='3e-5') 抛 TypeError: '<=' not supported between 'float' and 'str'—— 在模型已经构建完之后。这是集群提交时最容易踩的坑，因为命令行覆盖正是这样写的。

修法（三层）：

  1. _parse_scalar 先用正则识别科学计数法并转 float，整数仍保持 int；
  2. Config.validate 增加类型校验，字符串字段直接报 train.lr must be numeric, got str；
  3. 类型校验必须前移到所有范围比较之前并立即返回——否则字符串在 0 < value < 20 处先抛 TypeError， 精心写的错误消息根本走不到。

第 3 点是补测时测试自己抓到的我的错误：我先把类型检查追加在末尾， 测试立刻以 TypeError 而非断言失败告终，暴露出"类型检查必须最先执行"。

1.26 已修复 E1 只报告 Δt_lead，不报告 ΔR²_oos——文档两个结构性领先判据只接了一个

重读 1-priority-analysis.html 发现 H1 的结构性领先判据有两条（OR 关系）：

  • ① 匹配 FPR 下的预警领先步数 Δt_lead ≥ 50 步（已有）；
  • ② 跨步回归中 Sign_agree 相对 Acc_rank 的留出增量预测力 ΔR²_oos > 0（未接入）。

LagVerdict 和 predictive_gain 都已实现且有测试， 但 lead_time_from_arms 只调用了 matched_fpr_lead_time， 把结果直接返回——ΔR²_oos 路径是空的。E1 输出的 structural_lag 字段只有 dt_lead，没有 delta_r2_oos。

修法：lead_time_from_arms 现在同时计算两个判据并返回 LagVerdict.as_dict()，LagVerdict.met 按 OR 逻辑返回 （任一判据满足即支持结构性领先）。ΔR²_oos 的目标变量是 ΔFM（前向指标 step-to-step 变化），基预测器是审计线 acc_rank， 额外预测器是 sign_agree，留一法分组。

短夹具（4 个测量点）下 ΔR²_oos 返回 null—— ΔFM 只有 3 个差分，守卫要求 ≥ 5。 真实跑（300 步、log_every=10）会得 30 个点，完全够用。 这不是缺陷，而是"小数据集上诚实地不报告，而不是硬算出噪声"。

1.38 已修复 ΔR²_oos bootstrap CI 因 np.unique 把带替换采样降级为不带替换子采样

predictive_gain() 中 bootstrap 循环写成： 

idx = np.unique(np.concatenate([rng.integers(0, n, size=n)]))

np.unique 去除了重复索引，使每轮实际保留约 63% 的样本（1 − e⁻¹）， 等效于不带替换的子采样而非带替换的 bootstrap。后果：CI 方差被低估， criterion_met（即 H1 结构性领先的第二判据 ΔR²_oos CI 下界 > 0）可能误判。

1.39 已修复 old_task_loss 符号颠倒——ΔL_old 正值误判为旧任务性能提升

old_task_loss()（e2_intervention.py）使用了错误的权重符号： 

return (nll * (1.0 - 2.0 * correct)).mean()   # 错误

当 correct=1 时权重为 −1，贡献项 = −NLL（即 +log_prob）， 意味着 损失越高则正确答案概率越大——这是奖励信号，不是损失信号。 当 correct=0 时权重为 +1，贡献项 = +NLL，意味着损失越高则错误答案概率越小——同样是"越好越高"。 因此 ΔL_old^(1st) = ∇L_old^⊤ Δθ > 0 实际表示"单步更新提升了旧任务表现"， 与论文 §H2 / C2 的要求（"正值表示直接推高旧任务损失即退化"）完全相反，导致 E2 协议 A 中 dL_old_1st 的符号倒置。

修复（将权重改为标准损失权重）：

return (nll * (2.0 * correct - 1.0)).mean()   # 正确

现在 correct=1 权重 +1（NLL 升 = 正确答案概率降 = 退化 ✓）；correct=0 权重 −1（不惩罚错误答案被遗忘）。
